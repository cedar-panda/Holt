# 規模風險

假設窗口與記憶都增長到數萬量級，以下是從目前資料流可以預期的先後風險。這不是壓測結果；實際瓶頸仍要用真實資料量測。

## 先卡住的地方

| 優先 | 子系統 | 可能先卡在哪裡 | 目前的緩衝 |
|---|---|---|---|
| 1 | 窗口與消息 | `conversations`／`messages` 列表、歷史載入、續章候選 | conversation ID、分頁／範圍查詢、窗口摘要游標 |
| 2 | 記憶召回 | 觸發詞比對、FTS5／BM25 與向量結果合併 | 輕量索引先選候選、有限召回、LRU 正規化快取 |
| 3 | 摘要 | 摘要段、標籤、修復與失效鏈增長 | 摘要來源範圍、段落索引、有效性與回收流程 |
| 4 | Prompt live state | 多個功能同輪注入造成 token 與注意力壓力 | 各服務的條數／字數預算、request-only 區隔 |
| 5 | RP 世界書 | 整理批次、重複審核與條目召回 | 故事線 scope、同步 cursor、條數／字數上限 |
| 6 | RP 投影 | 人物、關係、狀態與來源版本一致性 | entity ID、`replaces_state_keys`、來源證據與 projection revision |
| 7 | keep-alive／cache | 快照序列化、背景喚醒、cache namespace 數量 | 窗口身分隔離、租約、定時 ping 與恢復 |
| 8 | 備份／匯入 | 全表掃描、媒體打包、FTS5 重建 | 明列 app tables、媒體去重、大小上限、transaction |

## 數萬記憶時

- 不應把所有記憶正文直接注入；先用索引取得候選，再由正文與 scope 驗證。
- 標籤數量會先增加 Prompt 選擇與去重成本；標籤應是索引，不是第二份正文。
- 向量索引、FTS5 與永久記憶若不同步，會出現「資料存在但搜不到」而不是單純變慢。
- 歸檔與拒絕墓碑若無界增長，去重與過濾也會變重；清理策略需要單獨壓測。

## 數萬窗口時

- 首頁／角色窗口列表應避免每次載入完整消息與完整摘要。
- 續章選擇只需要候選窗口、故事線、最新摘要／時間，不應查全量正文。
- 回覆 revision、分支與失效鏈會比一般窗口更快膨脹，應確認索引與保留政策。
- keep-alive 只能保留當前活動窗口；不能讓每個歷史窗口都進入背景任務。

## Prompt 與成本

- 固定前綴越穩定越容易由 provider cache 處理；live state 應保持小且只放本輪需要的資料。
- RP 續接、摘要固定區、關鍵詞召回、世界書與時間線要共用總預算，否則單項上限相加仍會爆量。
- provider 的 cache TTL、門檻、計費與命中欄位各不相同，必須用回傳 usage 觀測，不以本地 token 估算當最終答案。

## 備份與維護

- 完整備份會讀所有 app-owned tables；數萬窗口／消息與大量媒體會先卡 I/O、壓縮和暫存空間。
- 匯入覆蓋前應保留外部備份；雖然 service 使用驗證與 transaction，媒體與平台檔案仍是獨立風險。
- 任何新表、新索引或新 scope 都要同步加入備份 manifest、恢復順序與系統地圖。

## 建議的量測指標

- 窗口列表、續章候選、記憶召回、摘要生成、世界書整理各自的耗時。
- 每輪 static/profile/window/control/live token 數與 provider 回傳 cache usage。
- 召回候選數、去重後數量、實際注入段落數。
- 備份資料大小、媒體大小、匯入 transaction 時間與 FTS5 重建時間。
