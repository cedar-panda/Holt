# 舊記憶整理、永久記憶防護與蛛網關係完善報告

日期：2026-08-06  
範圍：待辦 2、3、5（向量化仍不在本次範圍）

## 完成摘要

本次把三件事接成同一條安全流程：

1. 舊記憶可以批次做零 token 的本地掃描，或由使用者手動交給摘要模型分析。
2. 掃描結果只會建立「關係建議」及「合併提案」，不會直接改寫、封存或刪除既有記憶。
3. 永久記憶的合併、取代與刪除加入第二次文字確認；封存區支援批次復原及批次永久刪除。
4. 蛛網關係升級成可追蹤的資料：關係類型、強度、狀態、來源、原因都有保存，舊連線會在資料庫升級時補齊預設值。
5. 蛛網形狀不變；新增關係篩選、詳情、確認／否決、鄰居高亮及無連線時的掃描入口。

## 2．既有普通記憶批次掃描

### 使用方式

在記憶頁多選記憶後，原本的「分析」入口改為「處理」，使用者可以自行選擇：

- **本地掃描 · 0 tokens**：使用字詞正規化、內容重合、分類、觸發詞及狀態衝突做比對。
- **摘要模型分析 · uses tokens**：沿用使用者已設定的摘要模型，適合語意較隱晦的關係；只有手動啟動時才發送。

本地掃描只比較同一角色、同一記憶模式、仍然有效的記憶。每次最多處理 500 條記憶、每條最多保留 4 個高價值關係、整輪最多產生 250 個新建議，避免大量舊資料讓介面或資料庫失控。

### 判斷結果

掃描器會把候選關係分成：

- `duplicate_candidate`：高度近似，另外建立可審核的合併提案。
- `conflict_update`：像是「以前住台北／現在住高雄」的狀態更新或矛盾，不會誤當重複記憶合併。
- `same_event`：同一事件的不同描述。
- `related`：有明確觸發詞或內容關聯，但不足以視為同一條。
- `temporal`：摘要模型判斷出的時間關係。

被使用者否決過的同一對記憶會保留 `rejected` 判定，因此下次掃描不會再次騷擾使用者。

### 安全邊界

- 掃描不會自動刪除、封存、合併或改寫舊記憶。
- `duplicate_candidate` 只進入 Memory 提案匣，由使用者選擇保留、編輯後合併或拒絕。
- 合併預覽可編輯；合併後是否永久會繼承任一來源記憶的永久狀態。
- 模型回傳的關係同樣先保存為 `suggested`，不會直接變成已確認事實。

## 3．永久記憶與批次操作防護

### 永久記憶二次確認

當提案會刪除、取代或合併永久記憶時，流程現在是：

1. 顯示動作內容與影響範圍，先做普通確認。
2. 再要求手動輸入 `PERMANENT` 才可執行。

在記憶列表直接封存一批記憶時，如果其中包含永久記憶，也會在普通確認後要求第二次輸入 `DELETE`。取消任一步都不會改動資料。

### 封存區批次安全操作

封存區現在支援：

- 多選／全選。
- **批次復原**：整批使用同一個資料庫交易；任一項失敗就整批回滾。
- **批次永久刪除**：必須輸入 `DELETE`；整批同樣是單一交易。
- 單條復原與刪除仍保留，避免小操作被迫進入多選模式。

這取代了「滑動後立即刪除」式風險流程。刪除不再因誤觸立即發生，也不再依賴短暫的撤銷提示。

主要實作：

- `lib/memory/database.dart`
- `lib/screens/memory_screen.dart`
- `lib/widgets/memory_review_tab.dart`

## 5．蛛網關係資料與可視化

### 資料層

資料庫版本升級至 v40。每條蛛網連線現在保存：

| 欄位 | 用途 |
|---|---|
| `relation_type` | related、same_event、temporal、duplicate_candidate、conflict_update |
| `strength` | 0–1 關係強度 |
| `status` | suggested、confirmed、rejected |
| `source` | legacy、local_scan、model、user、merge_remap |
| `reason` | 可讀的判斷原因 |
| `updated_at` | 最近處理時間 |

舊版已存在的連線不會丟失。升級時會補成 `confirmed + related + legacy`，並以原建立時間回填更新時間。舊備份缺少新欄位時使用相同預設值，因此不需要重新建立記憶。

資料庫同時保證：

- 連線兩端必須屬於同一角色，而且記憶仍然有效。
- 本地掃描／模型不能覆蓋使用者已確認或已拒絕的決定。
- 拒絕採軟狀態保存；圖上不顯示，但後續掃描可用它防止重複提案。
- 合併記憶時只轉移已確認的外部連線；未決建議不會被當成事實繼承。

### 蛛網呈現

蛛網既有形狀與美術語言完全保留，只增補關係表達：

- 已確認：實線與原有流光。
- 待確認：靜態虛線。
- 高度重複：較粗虛線及 `≋` 標記。
- 衝突／狀態更新：分段線及 `!` 標記。
- 不只用顏色表達狀態，降低色覺差異造成的辨識問題。
- 點選記憶會突出一跳鄰居、弱化無關節點；點空白處恢復。
- 右上角連線數可以開啟可搜尋／篩選的關係清單，作為小螢幕上點線不精準時的替代操作。
- 0 條連線但至少有 2 條記憶時，畫面直接提供「掃描既有記憶 · 0 token」。
- 關係詳情可確認、標記不相關、解除已確認連線，或直接前往重複記憶提案。
- 遵守系統的減少動態效果設定；關閉動畫後仍保留所有靜態狀態差異。

### 關係不會偷偷改變記憶權重

只有 `confirmed` 連線會參與神經傳播、觸發分數與封存島保護。`suggested` 連線不會提高記憶活躍度，也不會阻止記憶進入封存；這避免模型只因「猜測相關」就暗中改變記憶壽命。

主要實作：

- `lib/memory/database.dart`
- `lib/memory/spider_web_core.dart`
- `lib/widgets/spider_web_graph_view.dart`
- `lib/screens/memory_screen.dart`

## Cache、System Context 與用量影響

本次沒有修改聊天請求的 message role、動態 System Context 分層或既有 provider cache 邏輯。

- 本地掃描完全在手機端完成，0 token、0 API 請求，不會刷新或截斷對話 cache。
- 摘要模型分析只有使用者手動選擇後才呼叫；它是獨立工具請求，會正常記入模型用量，但不會插入聊天歷史或改寫當輪 user message。
- 關係建議、拒絕狀態及提案只寫入本地資料庫；下一輪聊天仍由既有記憶檢索規則決定是否注入。
- 本次沒有把新的記憶管理文字塞入 user message，也沒有增加每輪固定 token 消耗。

## 介面決策

本次依照現有產品風格增量修改，沒有重畫蛛網。安全操作採「普通動作在前、破壞性動作在後」的層級；主要新增操作維持至少 44 px 觸控區。關係同時提供線條樣式、符號及文字標籤，不依賴單一顏色；精細的畫布操作則另外提供清單入口。
