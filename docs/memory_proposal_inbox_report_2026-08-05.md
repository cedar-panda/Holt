# 記憶提案匣實作報告

日期：2026-08-05

## 本次結果

已將模型的記憶刪除與合併改為「先提案、後確認」。模型不再能因為 `<memo_del>` 或 `<memo_merge>` 直接改動現有記憶。

完整路徑為：

1. 模型在回覆中提出刪除或合併。
2. App 在本地建立不可直接執行的提案快照。
3. AI 回覆入庫後，提案綁定該則真實 message ID。
4. 聊天中的 `Thinking` / `Memory` 顯示待確認徽章。
5. 點擊徽章直達記憶頁的「待確認」分頁，並只顯示這則回覆的提案；使用者可切回全部提案。
6. 使用者選擇確認、稍後或拒絕。

## UI 結構

記憶頁固定為三個同級分頁：

- 記憶
- 待確認
- 摘要

待確認數量顯示在中間分頁；有未讀提案時使用淺紅色，全部已看過時轉為中性色。聊天內徽章同樣區分未讀與已讀，「稍後」不會繼續以紅色催促。

每個提案會展示：

- 動作類型與涉及數量。
- 原記憶 ID、類別、內容與永久記憶標記。
- 合併後的內容與觸發詞預覽。
- 失效或套用失敗原因。

## 防護邏輯

### 確認前零改動

提案建立時只讀取目標記憶並儲存快照，不會：

- 改變記憶 status。
- 新增合併後記憶。
- 改動蛛網連線。
- 寫入回收區。

### 變更偵測

提案會記錄每條目標記憶的 `status` 與 `updated_at`。確認時若任一目標已被其他操作更改，舊提案會轉為 stale，不套用舊決定。

### 交易式執行

確認合併後，以單一 SQLite transaction 完成：

1. 建立合併後記憶。
2. 將原記憶的外部蛛網連線轉移至新記憶。
3. 原記憶進入可還原的回收區。
4. 將提案標為完成。

任一步失敗會回滾，不留下半套狀態。

### 去重與拒絕尊重

相同角色、動作、目標 ID 與記憶版本生成唯一 fingerprint。模型重複提出同一件事時只保留一個提案；使用者拒絕後，同一版本不會反覆重建提案。

## 舊記憶與備份

- 資料庫 schema 由 v38 升至 v39，只新增 `pending_memory_actions`，不重寫現有記憶。
- 舊記憶不需轉換，不會自動產生提案。
- 新備份包含提案匣資料。
- 舊 v5 備份即使沒有新表仍可匯入，匯入後以空提案匣開始。

## System context 與 cache 影響

本次沒有修改：

- system context 分層。
- 模型請求 message role 或 content blocks。
- 記憶能力的靜態 prompt 文字。
- provider cache channel、cache key 或前綴順序。

提案是在回覆返回 App 後才進行的本地資料處理，不會把提案內容塞入 user message，也不會因徽章、分頁或確認操作刷新模型 cache。
